# Existing P0 Server Action contracts

`server-actions.json` is generated from the exported functions in the actual `"use server"` action files. CI rejects inventory/signature drift. These actions use Next.js's internal form/action transport, with build-specific action identifiers; they are not stable public REST endpoints. OpenAPI describes the versioned HTTP APIs separately. Do not create replacement auth/onboarding/team implementations to document them.

Every venture reference is untrusted input. Actions reauthenticate from server cookies; domain modules resolve permissions/membership again inside RLS transactions. UI hiding grants no authority. Unknown and inaccessible active ventures remain indistinguishable; errors never create a requester-visible access-request status endpoint (ADR-0013).

| Surface | Module / canonical route | Inputs and result | Authority / safeguards |
|---|---|---|---|
| Auth | `identity`, `/auth/*` | Register: name/email/password/confirmation; login: email/password/safe next; verification/recovery tokens; MFA code or recovery code. `FormState` errors/success or a validated redirect. See `src/app/auth/actions.ts` and identity policy. | Public identity operations have Origin/CSRF, account/IP limits, non-enumeration and single-use verification/reset rules. MFA requires a pending sign-in challenge. Cookie-only, revocable database sessions. |
| Profile/security | `identity`, `/settings/profile-security` | Name update; current/new/confirmed password; MFA enrol/confirm/disable/recovery-code regeneration; own session revocation. `SettingsState`, optional one-time enrol/recovery data, or reauthentication redirect. | Authenticated self only. Sensitive operations recheck password/session freshness; TOTP/recovery replay protection and atomic security audit apply. Other sessions are revoked after password change. |
| Create venture | `ventures`, `/onboarding` | Name and request UUID; `ActionResult` validation or redirect to the draft business step. | Authenticated account; request UUID makes draft creation retry-safe. Venture/membership/onboarding/audit/billing provisioning commit together. No worker is required for this small atomic operation. |
| Business setup | `ventures`, `/onboarding/[ventureId]/business` | Name, legal name, company number, sector, ISO reporting currency, timezone and fiscal year start month. Companies House lookup is read-only; user decides whether to apply it. Validation errors retain fields; success redirects to the next step. | Active draft Owner, independently checked by module/RLS. Inputs normalize through `businessDetailsInput`; company lookup has bounded adapter behavior and rate limits. Real provider verification remains separate. |
| Data review / activate | `ventures`, onboarding data/review routes | Explicit review and completion actions; persisted connection status and server-authoritative activation; `OnboardingFormState` error or complete. | Draft Owner. Complete state is UI feedback for already committed activation. P1 OAuth is not silently presented as complete. |
| Team | `memberships`, `/v/[ventureId]/settings/team` | Invite email/role; invitation ID to revoke; membership ID/role or suspend/reactivate/remove and expected version; access request ID with role to approve/reject. `TeamFormState` with success/error. | Active Admin/Owner with the specific capability; hierarchy/Owner invariants enforced by both module and database. Rechecks membership inside mutation transaction. Version conflicts prevent stale updates. Invitations expire, are single use and bound to verified email; mutations audit atomically. |
| Accept invite | `memberships`, `/invite/[token]` | Preview plus explicit accept token action; success goes to the accessible venture. Account switch retains the invitation route. | Signed-in verified account whose email equals the invitation. Unknown/expired/revoked tokens fail safely. No mutation on link preview. |
| Request access | `memberships`, `/v/[ventureId]/request-access` | Explicit request action with a venture reference; generic submitted state. | Authenticated, bounded pending requests, idempotent submission. Same response for unknown/inaccessible ventures; no requester-readable status API. |
| Command tasks | `command`, `/v/[ventureId]/command` | Add: request UUID, title (1–200), priority (high/medium/low), optional due date (YYYY-MM-DD). Complete/reopen: task ID and explicit target status. `TaskFormState` with success, or errors that keep the submitted values. The read snapshot is `GET /api/v1/command` (OpenAPI). | Active Operator+ (`command:manage_tasks`), resolved again by the module. RLS lets every member read and only Operator+ write, as themselves, with status-only updates and no deletes (migration 0014). The request UUID makes creation retry-safe; an explicit target status makes completion retries harmless. Creation and status changes are audited atomically with metadata that never includes the title. 200 additions per member per venture per hour. |
| Notifications | `notifications`, `/settings/notifications-activity` | Display cutoff and optional own notification ID; status message, then revalidated feed. Same module as OpenAPI REST. | Self inbox; cutoff-safe/idempotent read state. Venture activity requires independently resolved active Owner/Admin. |
| Support | `support`, `/support` | Request UUID, bounded subject/description; persisted request or validation/conflict error. Same module as OpenAPI REST. | Account-owned FORCE RLS, rate limit, atomic metadata-free audit and retry-safe identical payload. No SLA or staff impersonation is implied. |
| Billing | `billing`, `/settings/billing` | Billing account UUID, request UUID, checkout/portal command; status and validated Stripe URL for explicit navigation. Same module as OpenAPI REST. | Active billing-account Owner, independent of venture role; rechecked under lock. Server-selected price/customer, no client provider IDs, idempotent checkout and signed webhook mirror. Unconfigured provider returns unavailable. |

Dates returned through HTTP contracts use UTC ISO 8601; money uses integer minor units and ISO currency. Server form states may contain safe user-facing validation messages and field errors; structured account API errors carry a correlation ID, and identity HTTP responses carry `x-correlation-id`. Raw tokens, credentials and unnecessary personal information must not enter telemetry.
