# ADR-0007 — Database roles, tenant context and RLS

- Status: Accepted
- Date: 2026-10-03

## Context
Spec §6/§15/§16 and ADR-0002: PostgreSQL RLS must independently enforce venture isolation, covering reads, writes, updates and deletes; background jobs run with an explicit venture and service identity.

## Decision

### Roles (created by `pnpm db:bootstrap`, idempotent)
| Role | Login | Attributes | Purpose |
|---|---|---|---|
| `dxo_migrator` | yes | owns schema; not superuser | Runs migrations (release step only). Never available to web/worker at runtime. |
| `dxo_app` | yes | NOBYPASSRLS, owns nothing | Web and worker runtime. |
| `dxo_auth` | yes | NOBYPASSRLS, owns nothing | Better Auth identity store (users, sessions, credentials). No access to venture data. |
| `dxo_definer` | **no** | BYPASSRLS | Owns the few `SECURITY DEFINER` functions; minimal table grants. |

All tables use `ENABLE` + `FORCE ROW LEVEL SECURITY`. Grants are explicit per table in migrations (no default privileges).

### Tenant context
Every runtime query runs inside `withUser`, `withTenant` or `withService` (`src/platform/db/context.ts`), which opens a transaction and sets transaction-local settings (`set_config(..., true)`): `app.actor_type`, `app.user_id`, `app.service_id`, `app.venture_id`. Settings are discarded at commit/rollback, so pooled connections (including transaction-mode poolers) cannot leak context. Missing context fails closed.

### Policies
- Venture-owned tables: `app.apply_tenant_policies(table)` creates SELECT/INSERT/UPDATE/DELETE policies requiring `venture_id = current venture` **and** an active membership (or matching service scope), evaluated once per statement.
- `ventures` and own `venture_memberships` rows are listable without an active venture (venture switcher).
- Membership writes: Owner manages any non-owner row; Admin manages Manager/Operator/Viewer only; Owner rows are never written through tables (ownership transfer will be a dedicated audited function). No hard deletes.
- Ventures are created only via `app.create_venture()` (venture + Owner membership atomically).
- `users`: `dxo_app` gets column-restricted read of self and co-members only.
- Fine-grained permissions remain in the application RBAC layer; RLS enforces tenancy plus the minimum role rules for team management.

### Migrations
Table DDL is generated by Drizzle Kit from `src/platform/db/schema`. Roles, grants, policies and functions are hand-written SQL migrations (`drizzle-kit generate --custom`). Migrations are forward-only; recovery is via expand/contract changes and PITR (ADR-0010).

### Tests (`tests/rls`)
Catalogue tests fail the build if any table lacks forced RLS, if any granted command for a runtime role lacks a policy, if a runtime role can bypass RLS or owns objects, or if a `SECURITY DEFINER` function lacks a pinned `search_path`. Behavioural tests cover cross-venture reads/writes/deletes, forged context, service scope, role rules and context leakage across pooled connections.

## Consequences
Every P1+ venture-owned table must call `app.apply_tenant_policies` (or define equivalent explicit policies) and add explicit grants; the catalogue tests enforce this.
